    Product requirements · v1.2 draft

    Party Pop: shareable party invites with RSVPs

    Status: Draft for review Updated 11 Oct 2026 Stack: Next.js · Supabase · Vercel

    1Overview

    Parents organising a kid’s birthday party juggle invites across WhatsApp groups, class chats and Messenger, then chase replies by hand. Party Pop lets a host build a bright, comic-style invite in a couple of minutes, share it as a single link that shows a rich preview in chat apps, and see every reply in one place.

    Guests need no account and no app. They open the link, tap through to Google Maps for the venue and parking, and reply with their name and how many people are coming. Their reply is remembered on their phone so the same link lets them change it later.

    Working name. “Party Pop” is a placeholder used in the prototype. Final name and domain are an open question.

    2Goals & non-goals

    Goals

    • A host can create and share an invite in under 3 minutes on a phone.
    • Shared links show an image preview (photo, name, date) in WhatsApp, Messenger, iMessage and similar apps.
    • A guest can reply in under 30 seconds with no sign-up, and change their reply from the same link.
    • The host always knows the head count and can correct replies (for example, a reply sent by text message).
    • Installable PWA, usable offline for viewing an invite already opened.
    • Meets WCAG 2.2 level AA throughout.

    Non-goals for v1

    • Sending invites by email or SMS from the app (hosts share the link themselves).
    • Guest accounts, guest-to-guest visibility, or comments.
    • Payments, gift lists, or ticketing.
    • Push notifications and automated reminders (considered for v1.1).
    • Multiple co-hosts per event.
    • Native iOS or Android apps.

    3Users

    Host

    A parent planning a party for 10–30 children. Uses their phone in short bursts. Wants a nice-looking invite without design work, and a reliable head count for the venue and the cake.

    Guest

    Another parent in a class WhatsApp group. Opens the link once to reply, again on the day to find the venue and parking. May be using an older phone or a screen reader, and may reply on behalf of siblings.

    6Link previews in chat apps

    WhatsApp, Messenger, iMessage, Telegram and Slack fetch the page HTML without running JavaScript and read Open Graph tags. The invite page must therefore render its meta tags on the server.

    • og:title: “Maya is turning 6!”, or “Maya & Leo are turning 6 and 4!” for siblings.
    • og:description: “Sat 14 Nov, 2:00–4:30pm at Jump Planet. Tap to reply.”
    • og:image: an absolute HTTPS URL to a generated 1200×630 image, plus og:image:width, og:image:height, og:image:alt, and twitter:card=summary_large_image.
    • og:url and og:type=website; og:site_name set to the app name.

    The image is generated with Next.js opengraph-image.tsx (ImageResponse from next/og) at /i/[slug]/opengraph-image: each child’s photo in a comic burst (overlapping circles for siblings, up to three shown), the headline in the display font, and the date. Output as JPEG/PNG kept under 300 KB, because WhatsApp drops large images. The image URL includes a version parameter tied to events.updated_at so edits produce a fresh preview.

    Known limitation. Chat apps cache previews. A link already posted keeps its old preview after edits; the page itself is always current. QA uses the Facebook Sharing Debugger to refresh Messenger’s cache.

    7Guest RSVP identity

    Guests have no account. A guest’s right to change their reply comes from a secret token held in their browser.

    1. On first submit, the browser generates a 32-byte random token (crypto.getRandomValues).
    2. The client calls the submit_rsvp(slug, token, …) database function. The server stores only the SHA-256 hash of the token.
    3. Local storage keeps { rsvpId, token, name, coming, children, adults, note, updatedAt } under partypop.rsvp.{slug}.
    4. On return, the client calls get_my_rsvp(slug, token) and shows the server copy (so host edits win), falling back to the local copy when offline.
    5. Updating calls submit_rsvp with the same token, which updates the existing row.

    If a guest clears their browser data or uses another device, they appear as a new guest. The host can delete the duplicate. This trade-off keeps the guest flow free of sign-up.

    Abuse protection: a Vercel Firewall rate-limit rule on the RSVP endpoint (for example 10 submits per IP per minute), maximum 200 replies per event, and server-side validation of all lengths and ranges.

    8Magic link login

    • Supabase Auth signInWithOtp({ email, options: { emailRedirectTo } }) with the PKCE flow and an /auth/confirm route that verifies token_hash and sets the session cookie via @supabase/ssr.
    • Custom SMTP (for example Resend) with a branded template. The default Supabase mailer is rate-limited and not for production.
    • The email shows both the link and the 6-digit code ({{ .Token }}). On iPhone, a link opened from Mail launches Safari, not the installed home-screen app, and the two do not share a session. When the app runs in standalone mode, the “Check your email” screen leads with the code field.
    • Link expiry 1 hour, single use. Resend button disabled for 60 seconds, with the countdown announced to screen readers.
    • Email-scanner pre-fetching can consume single-use links. The confirm route therefore shows a “Sign in” button rather than signing in on a GET request.

    9PWA & install banner

    App shell

    • Web app manifest: name, short name, display: standalone, start_url: /dashboard?source=pwa, theme and background colours, 192 px and 512 px icons plus a maskable icon, and screenshots for the richer Android install sheet.
    • Service worker (Serwist): precache app shell and fonts; network-first for invite pages with cache fallback, so a guest who opened the invite can see the address at the venue without signal; offline page for everything else.
    • Never cache authenticated API responses in the shared cache.

    Install banner behaviour

    Decision. The banner is always shown in the browser, on every page, to hosts and guests alike. It has no close button. It is hidden only when the page runs as the installed app, or after a successful install in the current session.

    SituationBanner
    Opened from the installed app: matchMedia('(display-mode: standalone)') matches, or navigator.standalone === true on iOSNot rendered at all.
    Chromium browsers (Android Chrome, Edge, Samsung Internet, desktop Chrome)Capture beforeinstallprompt, call preventDefault(), show the banner with an “Install” button that calls prompt().
    Safari on iPhone and iPad (no install event)Banner shows the steps: tap Share, then “Add to Home Screen”, with the Share icon drawn inline.
    Browsers without install support (for example Firefox on Android)Banner shows the browser-menu steps for “Install” or “Add to Home screen”.
    After appinstalled firesBanner removed for the rest of the session.

    Wording depends on the page: host pages say “Get the Party Pop app”; invite pages say “Keep your invites on your home screen”.

    Layout: fixed to the bottom of the viewport, full width, with env(safe-area-inset-bottom) padding. The page reserves its height as bottom padding and sets scroll-padding-bottom so nothing, including a focused field, is hidden behind it. It is a labelled landmark (<aside aria-label="Install the app">), not a dialog: it never takes focus and does not block the page. Standalone detection runs before first paint (inline script setting a class on <html>) so the banner never flashes in the installed app.

    9bGuest app mode

    There is one PWA for everyone. What it shows depends on who opens it.

    • The manifest’s start_url is /app. That route sends a signed-in host to /dashboard, and anyone else to /me (My invites).
    • /me lists the invites opened on this device, read from local storage and refreshed with get_invites(slugs[]), which returns only public invite fields for the slugs given. A guest can never list or discover other invites.
    • The guest app has no host navigation. Signing in turns the same app into the host app; a host also keeps their own “Invites I’ve received” list.

    iPhone storage hand-off

    On iPhone and iPad, a home-screen app gets its own storage, separate from Safari. A guest who replied in Safari would open the installed app to an empty list. To carry their invites across:

    1. On invite pages, the browser creates a short-lived hand-off code holding the device’s invite list and tokens (create_handoff(payload), valid 30 minutes, single use).
    2. The page points <link rel="manifest"> at /manifest.webmanifest?h={code}, whose start_url is /app?h={code}.
    3. On first launch the app redeems the code, saves the invites and tokens to its own storage, and removes the code from the URL.

    On Android and desktop Chromium the installed app shares storage with the browser, so no hand-off is needed.

    10Accessibility (WCAG 2.2 AA)

    • Contrast: body text at least 4.5:1, large text and UI borders at least 3:1. Every palette pairing is listed in the design tokens with its ratio. White on red #C70F37 is 5.9:1; ink on yellow #FFD23F is 13:1.
    • Type: the comic display face is used only for headings at 24 px and above, never for body copy, form labels or long text. Body text is a rounded sans at 16 px minimum. Text resizes to 200% and reflows at 320 px without sideways scrolling.
    • Status never by colour alone: replies show “Coming” / “Can’t come” as text with an icon.
    • Forms: every field has a visible label; errors are text, linked with aria-describedby, and focus moves to the first invalid field. Steppers are real buttons with labels plus a typeable number input.
    • Navigation: breadcrumbs as a labelled nav landmark with aria-current="page" on the last item; link targets at least 24 px tall.
    • Keyboard and focus: everything reachable by keyboard in a logical order; a 3 px focus outline with 3:1 contrast; focus moves to the new heading on screen change; fixed banner never covers the focused element (2.4.11).
    • Targets: at least 24×24 px (2.5.8); the design uses 44 px for primary controls.
    • Announcements: “Reply saved”, “Link copied” and similar messages use a polite live region.
    • Images: each child’s photo has host-editable alt text; decorative bursts and halftones are hidden from assistive tech.
    • Motion: the small “pop” animations are removed under prefers-reduced-motion. No flashing.
    • Language and names: lang="en-GB"; unique, descriptive page titles; links say where they go (“Open venue in Google Maps”).
    • Login (3.3.8): magic link and code entry need no memorised password or puzzle; the code field supports paste and one-time-code autofill.
    • Testing: axe-core in CI (Playwright) with zero violations, Lighthouse accessibility 100, manual passes with VoiceOver on iOS and TalkBack on Android before launch.

    12Architecture

    • Frontend: Next.js (App Router, TypeScript), Tailwind CSS, deployed on Vercel. Invite pages use dynamic server rendering with a short cache (revalidate on edit via revalidatePath).
    • Database and auth: Supabase Postgres with Row Level Security on every table; Supabase Auth for magic links.
    • Files: Supabase Storage bucket invite-photos; path {event_id}/{uuid}.jpg.
    • Guest writes: Postgres functions (security definer) called through the Supabase client, so the anonymous role never gets direct table access.
    • Validation: Zod schemas shared by forms and server actions; matching check constraints in SQL.
    • Environments: Vercel preview deployments per pull request, a Supabase branch for preview, production project for main.

    13Data model

    create table events (
  id            uuid primary key default gen_random_uuid(),
  owner_id      uuid not null references auth.users on delete cascade,
  slug          text not null unique check (char_length(slug) = 10),
  starts_at     timestamptz not null,
  ends_at       timestamptz,
  timezone      text not null default 'Europe/London',
  venue_name    text not null,
  venue_address text not null,
  venue_maps_url   text,
  parking_notes    text,
  parking_maps_url text,
  directions    text,
  message       text check (char_length(message) <= 1000),
  rsvp_by       date,
  rsvps_open    boolean not null default true,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

-- One row per birthday child; siblings share an event
create table event_children (
  id         uuid primary key default gen_random_uuid(),
  event_id   uuid not null references events on delete cascade,
  position   smallint not null check (position between 1 and 4),
  name       text not null check (char_length(name) between 1 and 60),
  age        smallint check (age between 1 and 18),
  photo_path text,
  photo_alt  text,
  unique (event_id, position)
);

create table rsvps (
  id           uuid primary key default gen_random_uuid(),
  event_id     uuid not null references events on delete cascade,
  token_hash   text,                -- null when added by the host
  name         text not null check (char_length(name) between 1 and 80),
  attending    boolean not null,
  children     smallint not null default 0 check (children between 0 and 15),
  adults       smallint not null default 0 check (adults between 0 and 10),
  note         text check (char_length(note) <= 500),
  last_edited_by text not null default 'guest' check (last_edited_by in ('guest','host')),
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now(),
  unique (event_id, token_hash),
  check (not attending or children + adults >= 1)
);

alter table events enable row level security;
alter table rsvps  enable row level security;
alter table event_children enable row level security;

-- Hosts manage their own events and the replies to them
create policy "own events" on events for all
  using (owner_id = auth.uid()) with check (owner_id = auth.uid());
create policy "own children" on event_children for all
  using (exists (select 1 from events e where e.id = event_id and e.owner_id = auth.uid()));
create policy "own replies" on rsvps for all
  using (exists (select 1 from events e where e.id = event_id and e.owner_id = auth.uid()));

-- Guests: no table grants. Access only through these functions:
--   get_invite(slug)                     -> public invite fields and children, no owner data
--   submit_rsvp(slug, token, name, attending, children, adults, note) -> rsvp id
--   get_my_rsvp(slug, token)             -> that guest's reply only
--   get_invites(slugs[])                 -> public fields for the guest app list
--   create_handoff(payload) / redeem_handoff(code) -> iPhone storage hand-off

    14Privacy & safety

    Invites contain children’s photos, names, ages and a time and place. Treat them as sensitive.

    • Unguessable links; invite pages send X-Robots-Tag: noindex and are excluded from the sitemap.
    • Photos are re-encoded on the device before upload, removing EXIF location data.
    • Photos are stored under random paths. They must be fetchable by chat-app crawlers for previews, so the bucket is public-read by path but not listable. Hosts can choose “No photo in preview” to use an illustration instead.
    • Events and photos are deleted automatically 60 days after the party date; the host is told this when creating the invite.
    • Guests see a short notice by the form: their name and reply are shared only with the host.
    • UK GDPR: privacy notice, data export and deletion for hosts; guest data deletion on request via the host.

    17Decisions & open questions

    Decided

    • The install banner is always shown in the browser and cannot be dismissed.
    • Guests see the banner too. Their installed app shows only the invites they’ve received.
    • Replies record children and adults separately.
    • One invite can cover siblings (up to 4), each with their own name, age and photo.
    • No head-count cap; replies stay open unless the host switches them off.
    • Replies don’t ask for the children’s names; the reply name (for example “Theo & family”) is enough.
    • Breadcrumbs appear at the top of every page.
